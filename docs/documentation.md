# Документация

Раздел описывает, как писать и оформлять тексты: README, инструкции, справочники, ADR. Документация хранится рядом с кодом (Docs as Code).

## Читатель и цель (D-01)

**Правило.** Перед написанием определите читателя и результат. В начале документа в одном-двух предложениях сообщите, что читатель узнает или сделает.

## Один тип документа (D-02)

**Правило.** Каждый документ относится к одному типу модели Diátaxis: руководство (учит), инструкция (помогает решить задачу), справочник (описывает факты), объяснение (раскрывает причины). Типы не смешиваются в одном файле.

## README репозитория (D-03)

**Правило.** В README каждого репозитория есть разделы: назначение, требования, установка и запуск, запуск тестов, структура проекта, ссылки и контакты.

## Тон (D-04)

**Правило.** Обращайтесь к читателю на «вы» со строчной буквы. Пишите в активном залоге и настоящем времени. Не используйте оценочные слова: `просто`, `легко`, `очевидно`.

| Плохо | Хорошо |
|---|---|
| `Давайте просто нажмём «Сохранить». Файл будет сохранён приложением.` | Нажмите **Сохранить**. Приложение сохраняет файл. |

**Проверка:** Vale (Fillers, Passive).

## Длина предложений (D-05)

**Правило.** Одно предложение выражает одну мысль и содержит не более 25 слов. Абзац включает не более пяти предложений. Правило не относится к коду и таблицам.

## Терминология (D-06)

**Правило.** Одно понятие называется одним термином. Термины фиксируются в глоссарии. Жаргон не используется: `юзер` → «пользователь», `таска` → «задача», `фича` → «функция», `баг` → «ошибка», `залить` → «загрузить».

**Проверка:** Vale (Terms).

## Аббревиатуры (D-07)

**Правило.** При первом упоминании расшифровывайте аббревиатуру, если она не общеизвестна читателю: «REST (Representational State Transfer)».

## Структура инструкции (D-08)

**Правило.** Инструкция содержит: цель, предварительные условия, шаги, ожидаемый результат, действия при ошибке. Заголовок инструкции начинается с глагола или отглагольной формы («Создание заказа»).

## Заголовки (D-09)

**Правило.** В файле один заголовок первого уровня. Уровни не пропускаются: после H2 идёт H3.

**Проверка:** markdownlint (MD001, MD025).

## Шаги и списки (D-10)

**Правило.** Нумерованный список используйте для последовательности действий, маркированный — для равноправных элементов. Один шаг — одно действие, глагол в повелительном наклонении.

## Код и команды (D-11)

**Правило.** Код, команды, имена файлов и параметры пишите в обратных кавычках. Блоки кода сопровождайте указанием языка. Примеры должны запускаться. Секреты заменяйте плейсхолдерами.

| Плохо | Хорошо |
|---|---|
| `curl -H "Authorization: Bearer abc123"` | `curl -H "Authorization: Bearer <YOUR_API_KEY>"` |

**Проверка:** markdownlint (MD040).

## Ссылки (D-12)

**Правило.** Ссылки внутри проекта делайте относительными. Текст ссылки описывает цель перехода.

| Плохо | Хорошо |
|---|---|
| `Подробнее [здесь](install.md).` | `См. [руководство по установке](install.md).` |

## Иллюстрации и предупреждения (D-13)

**Правило.** Скриншот добавляйте, только когда текст не объясняет действие: формат PNG, ширина до 800 px, есть подпись, нет персональных данных. Предупреждения оформляйте блоками `note`, `warning`, `tip`, не более одного блока подряд.

## Документация вместе с кодом (D-14)

**Правило.** Изменение поведения и обновление документации выполняются в одном pull request.

## Архитектурные решения (ADR) (D-15)

**Правило.** Каждое значимое решение записывается в ADR по шаблону: контекст, решение, последствия, статус (предложено, принято, заменено).

```markdown
# ADR-007. Использовать PostgreSQL для хранения заказов

**Статус:** принято

## Контекст
Нужны транзакции и связи между сущностями.

## Решение
Используем PostgreSQL 16.

## Последствия
Нужно сопровождать миграции и резервное копирование.
```

## Описание метода API (D-16)

**Правило.** Для каждого метода API указывайте: заголовок «Метод <HTTP-метод> <путь>», описание, таблицу параметров, пример запроса и ответа, коды ответов и ошибок.
