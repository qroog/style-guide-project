# Тестирование

Раздел описывает, какие тесты писать и как их оформлять. Примеры даны для Go.

## Тест для каждого изменения (T-01)

**Правило.** Новая логика и исправленная ошибка сопровождаются тестом. Исправление ошибки начинайте с теста, который её воспроизводит.

## Пирамида тестов (T-02)

**Правило.** Пишите много модульных тестов, меньше интеграционных и мало сквозных (e2e). Чем выше уровень, тем медленнее и дороже тест.

## Структура теста (T-03)

**Правило.** Тест состоит из трёх частей: подготовка (Arrange), действие (Act), проверка (Assert). Один тест проверяет одно поведение.

## Имена тестов (T-04)

**Правило.** Формат: `Test<Что>_<Условие>_<Результат>`.

```go
func TestGetTask_NotFound_ReturnsError(t *testing.T) { … }
```

## Табличные тесты (T-05)

**Правило.** Для нескольких наборов данных используйте табличные тесты с `t.Run`.

```go
func TestAbs(t *testing.T) {
    tests := []struct {
        name string
        in   int
        want int
    }{
        {"positive", 3, 3},
        {"negative", -3, 3},
        {"zero", 0, 0},
    }
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            if got := Abs(tt.in); got != tt.want {
                t.Errorf("Abs(%d) = %d, want %d", tt.in, got, tt.want)
            }
        })
    }
}
```

## Независимость и повторяемость (T-06)

**Правило.** Тесты не зависят друг от друга, порядка запуска, текущего времени и сети. Время и случайные значения передавайте через параметры или интерфейсы.

## Зависимости и база данных (T-07)

**Правило.** Внешние зависимости подменяйте через интерфейсы. Код работы с базой данных проверяйте интеграционными тестами на настоящей СУБД (например, в Docker), а не моками.

## Покрытие (T-08)

**Правило.** Ориентир — не менее 70 % покрытия пакетов с бизнес-логикой. Покрытие не цель: важнее проверить поведение и граничные случаи. В CI запускайте `go test -race ./...`.

## Тестовые данные (T-09)

**Правило.** Используйте синтетические данные. Не применяйте персональные данные и реальные секреты.

## Понятные сообщения (T-10)

**Правило.** Сообщение об ошибке теста содержит полученное и ожидаемое значения: `got`, `want`.

## Тесты в CI (T-11)

**Правило.** Тесты запускаются на каждый pull request. Pull request с падающими тестами не сливается.
