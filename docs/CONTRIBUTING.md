# Как внести вклад в руководство по разработке

## Как предложить изменение

1. Для небольших правок (опечатки, примеры) сразу создайте pull request. Для новых правил или изменения существующих сначала откройте issue и опишите проблему и предложение.
2. Создайте ветку от `main` по формату `<тип>/<описание>` (правило N-09), например `docs/add-accessibility-rules` или `fix/glossary-typo`.
3. Внесите изменения, соблюдая само руководство.
4. Проверьте сборку и линтеры локально (см. ниже).
5. Откройте pull request с описанием: что изменено, зачем, как проверить.

## Требования к коммитам (Conventional Commits)

Формат: `<тип>(<область>): <описание>`. Область необязательна. Описание пишите в повелительном наклонении, до 72 символов, без точки в конце, со строчной буквы.

| Тип | Когда использовать |
|---|---|
| `feat` | новая функция |
| `fix` | исправление ошибки, опечатки, битой ссылки |
| `docs` | изменение документации |
| `test` | добавление или изменение тестов |
| `refactor` | перестановка и переименование разделов, изменение кода без смены поведения |
| `ci` | изменения workflow и линтеров |
| `chore` | прочие служебные изменения |

Примеры:

```text
docs: add text accessibility rules
fix(glossary): correct term definition
ci: add vale check to workflow
```

## Процесс ревью

1. Каждый pull request проверяет минимум один рецензент, не являющийся автором.
2. Автоматические проверки (markdownlint, Vale, commitlint, `mkdocs build --strict`) должны пройти до ревью.
3. Рецензент проверяет соответствие руководству по чек-листу из раздела «Ревью».
4. Комментарий содержит префикс важности (`blocker:`, `suggestion:`, `nit:`, `question:`, `praise:`), ссылку на правило (например, D-06) и предложение исправления.
5. Автор отвечает на каждый комментарий и вносит правки новыми коммитами.
6. После одобрения и успешных проверок выполняется squash merge в `main`, ветка удаляется.
7. После слияния сайт публикуется автоматически.

Первый ответ на pull request ~ в течение двух дней.

## Локальная сборка

```bash
git clone https://github.com/qroog/style-guide-project.git
cd style-guide-project
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
mkdocs serve               # просмотр на http://127.0.0.1:8000
mkdocs build --strict      # проверка сборки
markdownlint-cli2 "docs/**/*.md"
vale docs
```

## Как добавить новый раздел

1. Создайте ветку: `git switch -c docs/add-<раздел>`.
2. Создайте файл `docs/<имя-раздела>.md` (латиница, kebab-case) с одним заголовком первого уровня.
3. Для каждого правила укажите идентификатор, формулировку, причину, пример «плохо / хорошо» и способ проверки.
4. Добавьте раздел в `nav` файла `mkdocs.yml` в подходящую часть.
5. Если правило можно проверить автоматически, добавьте настройку линтера.
6. Обновите глоссарий, если появились новые термины.
7. Выполните локальные проверки, сделайте commit и откройте pull request.
