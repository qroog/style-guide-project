# Ревью кода и документации

Раздел описывает, как готовить pull request и писать комментарии при ревью. Цель ревью — улучшить результат, а не оценить автора.

## Подготовка pull request (R-01)

**Правило.** Автор перед отправкой просматривает собственный diff. Описание pull request содержит: что изменено, зачем, как проверить, ключ задачи YouTrack.

```markdown
## Что изменено
Добавлено поле `delivery_status` в ответ API заказа.

## Зачем
PROJ-142: пользователи не видят статус доставки.

## Как проверить
`go test ./...`, затем GET /orders/1.
```

## Размер pull request (R-02)

**Правило.** Размер — до 400 строк изменений, одна цель. Большие изменения делите на несколько pull request.

## Комментируйте код, а не человека (R-03)

**Правило.** Формулируйте замечание о коде, а не о личности автора: «в этой функции…», а не «ты забыл…».

| Плохо | Хорошо |
|---|---|
| Ты забыл обработать ошибку. | В `GetTask` не обрабатывается ошибка `repo.Find`. |

## Структура комментария (R-04)

**Правило.** Комментарий содержит три части: что замечено, почему это важно (со ссылкой на правило), что предлагается.

> suggestion: в `GetTask` ошибка возвращается без контекста (C-06). Предлагаю обернуть её через `fmt.Errorf("get task %d: %w", id, err)`: тогда в логах видно, где она возникла.

## Префиксы важности (R-05)

**Правило.** Начинайте комментарий с префикса: `blocker:` (обязательно исправить до слияния), `suggestion:` (желательно), `nit:` (мелочь), `question:` (вопрос), `praise:` (отметка удачного решения).

## Вопросы вместо приказов (R-06)

**Правило.** Если причина неочевидна, задавайте вопрос: «Что произойдёт, если здесь придёт `nil`?»

## Хорошее тоже отмечайте (R-07)

**Правило.** В каждом ревью отметьте хотя бы одну удачную часть (`praise:`).

## Ответы и закрытие обсуждений (R-08)

**Правило.** Автор отвечает на каждый комментарий («Исправлено в `<хеш>`» или обоснованное несогласие). Обсуждение закрывает (Resolve) тот, кто его начал.

## Решение по ревью (R-09)

**Правило.** Approve ставится, только когда нет незакрытых `blocker:`. Решение Request changes сопровождается списком блокирующих замечаний.

## Сроки (R-10)

**Правило.** Первый ответ на pull request даётся в течение двух рабочих дней. Автор отвечает на замечания в течение двух рабочих дней.

## Что проверяет рецензент (R-11)

**Правило.** Рецензент проверяет по чек-листу: корректность, тесты, читаемость и именование, обработку ошибок, безопасность, SQL и миграции, документацию, соответствие критериям приёмки задачи.

## Чек-лист рецензента

- [ ] Изменение решает задачу и соответствует критериям приёмки.
- [ ] Есть тесты, они проходят в CI.
- [ ] Имена и комментарии соответствуют разделам «Наименование» и «Стиль кода».
- [ ] Ошибки обрабатываются, секретов в коде нет.
- [ ] SQL параметризован, миграции обратимы.
- [ ] Документация обновлена.
