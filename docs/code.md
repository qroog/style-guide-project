# Стиль кода и комментирование (Go)

Раздел описывает оформление кода на Go и комментарии. Правила опираются на соглашения языка (Effective Go, Go Code Review Comments).

## Форматирование и линтеры (C-01)

**Правило.** Форматируйте код командами `gofmt` и `goimports`. Линтер `golangci-lint` обязателен и запускается в CI.

```bash
gofmt -l .
golangci-lint run
```

**Проверка:** gofmt, golangci-lint.

## Комментарий объясняет причину (C-02)

**Правило.** Комментарий объясняет, **почему** код написан так, а не **что** он делает.

```go
// Плохо: пересказывает код
i++ // увеличиваем i на 1

// Хорошо: объясняет причину
retries++ // API иногда отвечает 503, повторяем запрос до трёх раз
```

## Документирующие комментарии (C-03)

**Правило.** У каждого экспортируемого идентификатора есть документирующий комментарий. Он начинается с имени идентификатора.

```go
// Плохо
// get task
func GetTask(id int) (*Task, error)

// Хорошо
// GetTask возвращает задачу по идентификатору.
// Если задача не найдена, возвращает ErrTaskNotFound.
func GetTask(id int) (*Task, error)
```

**Проверка:** revive (правило exported).

## Комментарий к пакету (C-04)

**Правило.** У каждого пакета есть комментарий вида `// Package name ...` в файле `doc.go` или в основном файле пакета.

```go
// Package order содержит бизнес-логику обработки заказов.
package order
```

**Проверка:** revive (правило package-comments).

## Язык комментариев (C-05)

**Правило.** Комментарии пишутся на русском языке во всём проекте. Единый язык важнее выбранного.

## Обработка ошибок (C-06)

**Правило.** Не игнорируйте ошибки. Оборачивайте их с контекстом через `%w`. Текст ошибки начинайте со строчной буквы, без точки и восклицательных знаков. Намеренно проигнорированную ошибку помечайте комментарием. `panic` допустим только для невосстановимых ошибок при запуске.

```go
// Плохо
return nil, errors.New("Error: " + err.Error() + "!")

// Хорошо
return nil, fmt.Errorf("get task %d: %w", id, err)

_ = f.Close() // ошибка закрытия файла на чтение не влияет на результат
```

**Проверка:** errcheck.

## Контекст (C-07)

**Правило.** Передавайте `context.Context` первым параметром функции. Не храните контекст в структурах.

```go
func (s *Service) GetTask(ctx context.Context, id int) (*Task, error)
```

## Ранний возврат (C-08)

**Правило.** Сначала обрабатывайте ошибки и граничные случаи, основной сценарий оставляйте без вложенности. Глубина вложенности — не более трёх уровней.

## Закомментированный код (C-09)

**Правило.** Не коммитьте закомментированный код. Лишнее удаляйте: история хранится в Git.

## TODO (C-10)

**Правило.** Оформляйте TODO в виде `TODO(автор): что сделать (PROJ-123)`, где `PROJ-123` — ключ задачи в YouTrack.

```go
// TODO(ivanov): добавить пагинацию (PROJ-142)
```

## Логирование (C-11)

**Правило.** Используйте структурированные логи и уровни (`debug`, `info`, `warn`, `error`). Не записывайте в логи секреты и персональные данные.

## Актуальность комментариев (C-12)

**Правило.** Обновляйте комментарий вместе с кодом. Устаревший комментарий хуже, чем его отсутствие.
