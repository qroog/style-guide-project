# Инженерный глоссарий и словарь написаний

Глоссарий фиксирует единые названия архитектурных компонентов, процессов и заимствованных терминов. Его цель — не борьба с живым языком разработчиков, а устранение смысловой путаницы (когда один и тот же механизм в разных разделах документации называют тремя разными словами) и устного жаргона в чистовых спецификациях.

## 1. Архитектура, код и инфраструктура

В этой таблице закреплены термины, которые чаще всего путают по смыслу или заменяют неоднозначным сленгом.

| Стандартный термин | Что означает в нашем проекте | Не используйте в доке (и почему) |
| :--- | :--- | :--- |
| **Эндпоинт** (или HTTP-метод) | Точка входа REST API (`POST /api/v1/tasks`) | `ручка`, `роут`, `урл` — устный сленг; `метод` — путается с методом структуры в Go |
| **Воркер** (Worker) | Фоновый процесс, вычитывающий задачи из очереди | `демон`, `таск-раннер`, `обработчик`, `крон` (если процесс работает непрерывно, а не по расписанию) |
| **Docker-образ** (Image) | Неизменяемый шаблон для запуска (`Dockerfile`) | `контейнер`, `докер`, `виртуалка` — путаница между шаблоном и запущенным процессом |
| **Docker-контейнер** | Запущенный в памяти экземпляр Docker-образа | `образ`, `виртуалка`, `инстанс докера` |
| **Переменные окружения** | Параметры конфигурации процесса из `.env` или ОС | `энвы`, `переменные среды`, `конфиги окружения` |
| **Миграция** | Версионируемый SQL/Go-скрипт изменения схемы БД | `апдейт базы`, `накатка схемы`, `патч БД` |
| **Полезная нагрузка** (`payload`) | Тело запроса или сообщения в очереди | `боди`, `дата` (`data` — путается с календарной датой) |
| **Идемпотентность** | Свойство операции выдавать тот же результат при повторном вызове | `безопасный повтор`, `защита от дублей` |

## 2. Процессы разработки и Git

Мы используем устоявшиеся в индустрии заимствования. Допускается как стандартная русская транслитерация, так и английские аббревиатуры — главное не использовать глагольный сленг в официальных гайдах.

| Стандартный термин | Определение | Не используйте в чистовой доке |
| :--- | :--- | :--- |
| **Pull Request (PR)** | Запрос на вливание ветки в `main` | `пулл-реквест` (с двумя «л»), `мерж-реквест` (термин GitLab, если проект на GitHub) |
| **Коммит** (`commit`) | Зафиксированное изменение в истории Git | `закоммитить`, `запушить` (заменяйте на: *«сделайте коммит»*, *«отправьте ветку»*) |
| **Код-ревью** (или ревью) | Проверка PR другими инженерами команды | `аппрувнуть`, `заревьюить` |
| **Деплой** (или развёртывание) | Выкатка и запуск новой версии сервиса на окружении | `выкатить в прод`, `залить на сервер` |
| **Баг** (или дефект / ошибка) | Некорректное поведение кода, требующее исправления (`fix`) | `косяк`, `глюк`, `багулина` |
| **Фича** (или функциональность) | Новая пользовательская или техническая возможность (`feat`) | `хотелка`, `доработка` |
| **Костыль** → **Временное решение** (`workaround`) | Обходное техническое решение с заведённым `TODO` | `костыль`, `хак`, `подпорка` (в документации и ADR пишем *«временное обходное решение / workaround»*) |

## 3. Принятые инженерные сокращения

Эти сокращения не требуют расшифровки внутри проектной документации для разработчиков:

* **ADR** (*Architecture Decision Record*) — запись об архитектурном решении в директории `docs/adr/`.
* **CI/CD** (*Continuous Integration / Continuous Delivery*) — пайплайн автоматической проверки, сборки и публикации.
* **DoD** (*Definition of Done*) — чек-лист критериев готовности задачи перед закрытием.
* **SemVer** (*Semantic Versioning*) — версионирование релизов в формате `MAJOR.MINOR.PATCH` (например, `v1.4.2`).
* **TTL** (*Time to Live*) — время жизни записи в кэше или токена авторизации.
* **RFC** (*Request for Comments*) — стандарт интернета (например, `RFC 3339` для времени) или проектный документ с предложением крупного изменения.
