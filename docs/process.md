# Процесс работы

Раздел описывает путь изменения от задачи до выпуска: ветки, коммиты, pull request, CI и критерии готовности.

## Ветки (P-01)

**Правило.** Создавайте ветку от `main` по формату из правила N-09. Ветка `main` защищена: прямые коммиты запрещены.

## Коммиты (P-02)

**Правило.** Оформляйте сообщения по Conventional Commits: `<тип>(<область>): <описание>`. Описание — в повелительном наклонении, до 72 символов, без точки. Один коммит — одно логическое изменение. Ключ задачи указывайте в теле коммита.

```text
feat(orders): add delivery_status to order response

PROJ-142
```

| Тип | Когда использовать |
|---|---|
| `feat` | новая функция |
| `fix` | исправление ошибки |
| `docs` | изменение документации |
| `test` | тесты |
| `refactor` | изменение кода без смены поведения |
| `ci` | настройка CI и линтеров |
| `chore` | прочие служебные изменения |

**Проверка:** commitlint.

## Pull request (P-03)

**Правило.** Заголовок pull request оформляется как сообщение коммита. Описание — по шаблону из правила R-01. Pull request связывается с задачей YouTrack.

## Слияние (P-04)

**Правило.** Слияние выполняется через squash merge после одобрения и успешного CI. Ветка после слияния удаляется.

## Обязательные проверки CI (P-05)

**Правило.** На каждый pull request запускаются: `gofmt`, `golangci-lint`, `go test -race ./...`, `sqlfluff`, `markdownlint`, `vale`, сборка документации.

## Версии и релизы (P-06)

**Правило.** Версии назначаются по SemVer (`vMAJOR.MINOR.PATCH`). Релиз помечается тегом, изменения записываются в changelog.

## Критерии готовности (Definition of Done) (P-07)

**Правило.** Задача готова, когда: код написан и соответствует руководству, тесты добавлены и проходят, документация обновлена, ревью пройдено, CI зелёный, состояние задачи в YouTrack обновлено.
