# Общие принципы разработки

Раздел описывает принципы, на которых основаны остальные правила. Если конкретного правила нет, руководствуйтесь ими.

## Простота (G-01)

**Правило.** Выбирайте самое простое решение, которое работает. Не добавляйте функциональность «на будущее» (принципы KISS и YAGNI).

**Почему.** Простой код легче читать, тестировать и менять.

## Читаемость важнее краткости (G-02)

**Правило.** Пишите код так, чтобы коллега понял его без вашей помощи. Код читают чаще, чем пишут.

| Плохо | Хорошо |
|---|---|
| `if !(a && !b) {…}` | `if !isAllowed(user) {…}` |

## Единственная ответственность (G-03)

**Правило.** Функция, тип или пакет решают одну задачу. Функция длиннее 50 строк — повод разделить её.

## Не дублируйте знания (G-04)

**Правило.** Одно знание хранится в одном месте (принцип DRY). Не объединяйте код, который похож только внешне.

## Явное лучше неявного (G-05)

**Правило.** Обрабатывайте ошибки, не используйте глобальное состояние и «магические» значения: выносите их в именованные константы.

```go
// Плохо
if retries > 3 { … }

// Хорошо
const maxRetries = 3
if retries > maxRetries { … }
```

## Небольшие изменения (G-06)

**Правило.** Один pull request — одна цель и не более 400 строк изменений. Крупную работу делите на части.

## Безопасность по умолчанию (G-07)

**Правило.** Не храните секреты (пароли, токены, ключи) в коде и репозитории. Проверяйте входные данные. Выдавайте минимально необходимые права.

## Улучшайте код постепенно (G-08)

**Правило.** Оставляйте код чище, чем нашли, но рефакторинг выполняйте отдельным коммитом, а не вместе с изменением поведения.

## Фиксируйте решения (G-09)

**Правило.** Значимые архитектурные решения записывайте в ADR (см. раздел «Документация»), чтобы причины не терялись.
